# JALORA Stage 1: Architecture Inventory and Frozen Baseline

**Authority:** Stage 1 of [the master implementation roadmap](./JALORA-MASTER-IMPLEMENTATION-ROADMAP.md).
**Scope:** source audit and baseline only. No product implementation is authorized by this report.
**Evidence rule:** distinguish code presence from production use, automated tests from live provider behavior, and observed outcomes from assumptions.

## Existing state and result contract

| Existing type | Reusable fields/state | Contract gap |
|---|---|---|
| `Task` / `TaskStep` (`backend/app/models/task.py`) | Stable IDs, owner/conversation/run, goal, plan, status/progress/timestamps, step index/description/status/dependencies/tool/arguments/detail. | Dependencies use indices rather than stable step IDs. No uniform typed input/output/evidence/verification, attempt/idempotency metadata, or approval foreign key across all paths. |
| `AgentRun` (`backend/app/models/agent.py`) | Stable ID, user/conversation, status/model, serialized graph state, error/timestamps. | Graph-specific state/status; not every entry path creates one. No uniform trigger, idempotency, or verification contract. |
| `Approval` | Stable ID, owner/run/tool/arguments/level/kind, optional plan-step ID, status/result/decision timestamps. Graph and email use an atomic pending→sending claim. | Empty `run_id` on standalone email; distinct executors and UI semantics. No general expiry/revocation/version history; edited payload lacks immutable approved revision. |
| `ActivityLog` | Tool, arguments, success/result summary, approval/provider/error metadata and timestamp. | No first-class task/step/evidence/result-state link; some linkage remains in free-form metadata. |
| Workflow execution/result | Durable execution ID, inputs/intermediates/outputs, ordered steps, status/result/error and timing. | Separate lifecycle and result vocabularies; no shared approval pause/resume. |
| `Call`, `Schedule`, `DeviceRemoteCommand` | Durable domain IDs, domain-specific statuses and timestamps; optional Call task/run links; schedule recurrence; device-command decision/expiry. | Separate status machines; no guaranteed canonical parent task/step or idempotency identity for every occurrence/action. |
| `UserAction`, `Outcome` | Fingerprint/retry-count/action information and outcome/quality metadata. | Not established as the common dispatch/reconciliation/result path. |
| Result types | `ToolResult(success,message,data,error)`, `ChatOutcome`, `TaskResult`, `WorkflowExecutionResult`, provider responses. | Differing, partly free-form shapes. No common result separating planned/prepared/approval/submitted/provider-accepted/delivered/verified/failed/unknown/rejected/cancelled. |

### Observed lifecycle/status values (inventory, not the Stage 2 contract)

| Record | Source-defined values or states | Notes |
|---|---|---|
| `Task.status` | `queued`, `running`, `waiting_for_approval`, `paused`, `completed`, `partial`, `failed`, `stopped`, `cancelled` | User-facing lifecycle; finalization maps graph states into this vocabulary. |
| `TaskStep.status` | `pending`, `active`, `done`, `failed`, `skipped` | Dependency references are task-step indices. |
| `AgentRun.status` | `running`, `completed`, `failed`, `partial`, `paused_approval`, `paused`, `stopped` | Does not list `cancelled` in the model comment, though task cancellation exists. |
| `Approval.status` | `pending` → `sending` → `approved` / `failed` / `outcome_unknown`; or `pending` → `rejected` / `skipped` | A durable claim exists; `sending` is an in-flight state, not provider acceptance. |
| `Call.status` | `dialing`, `in_progress`, `completed`, `failed`, `cancelled`, `no_answer` | Provider call lifecycle; does not itself mean the requested conversational outcome was verified. |
| `WorkflowExecutionRecord.status` | String field defaulting to `running` | Model has no enumerated status contract; engine uses its own result/status behavior. |
| `DeviceRemoteCommand.status` | `pending`, `approved`, `rejected`, `expired`, `opened`, `failed` | Specific to a scoped browser-link action; not a general agent outcome model. |
| `UserAction.status` | `executing`, `completed`, `failed`, `interrupted` | Fingerprint/retry record, not shown to be a universal execution boundary. |
| `Schedule` | `enabled`, `notify_only`, `next_run`, `last_run`; kind `once`, `cron`, `interval` | A schedule definition is not the status of an individual run/occurrence. |

**Stage 1 conclusion:** identifiers and persistence primitives already exist; the main gaps are inconsistent adoption, separate approval/execution state machines, untyped status/result/evidence, absent links on direct paths, and no uniform idempotency/reconciliation boundary. The completed Stage 2 design in [Canonical Execution Contract v1](./JALORA-CANONICAL-EXECUTION-CONTRACT-v1.md) therefore selects an additive extension of existing records plus a per-step attempt journal, not a wholesale task-manager/schema redesign. This Stage 1 snapshot is retained as the evidence baseline.

## Test and shared-UI baseline

### Test inventory

The checkout has 84 backend `test_*.py` modules and 8 React Playwright specs (40 declared browser tests). Exact full-suite results and warnings are recorded below. Tests that mock providers establish contract behavior, not live third-party delivery.

### Shared localhost observation

Supplied browser pages were inspected without submitting data or triggering actions. The active `127.0.0.1:5173` page displayed the login screen and logged 401 responses for unauthenticated resources. Other supplied tabs had stale `ERR_CONNECTION_REFUSED` or prior 500 events. No credentials were available; therefore authenticated shared-instance task/approval behavior could not be exercised. This is **unverified**, not a pass and not proof the authenticated application is broken. Use authenticated isolated Playwright tests for repeatable UI acceptance.

### Full-suite results

**Backend:** `python -m pytest -q` — **1,631 passed, 7 skipped**, 14 warnings, 698.96 seconds. Warnings include Python 3.12 `audioop` deprecation and `datetime.utcnow()` deprecations in creative tests.

**Frontend build:** `npm run build` — passed; existing Vite dynamic-import and large-bundle warnings were reported.

**Playwright full suite (isolated SQLite/backend/frontend ports):** Two full runs each reported **39 passed, 1 failed**. In the first (3.4 minutes), `e2e/regression.spec.ts:109`, “Workspace start-coding button,” failed because `.ws-bubble.user` was absent after `.ws-msg.user` appeared; its targeted rerun passed (**1 passed in 28.5 seconds**). In the second (4.8 minutes), `e2e/approval.spec.ts:36`, “can reject an approval request,” timed out waiting for the chat composer during `authenticatedPage` setup; its targeted rerun passed (**1 passed in 40.9 seconds**). The failures are different and neither reproduced in isolation. Both full runs also logged low-memory and local model-discovery warnings. This indicates suite/load sensitivity, but the cause is undetermined; **neither full run is a clean pass**.

**Shared localhost:** authenticated task/approval behavior was not verified. The active shared page showed login and 401s; other supplied tabs were stale/disconnected. No credentials were available. See the limitation above; do not treat isolated Playwright as proof of the shared instance or live providers.

**Baseline disposition:** source inventory, existing state/status mapping, and test evidence are recorded. The browser suite instability and unauthenticated shared-instance limitation are explicit baseline findings, not claims of successful acceptance. No product code was changed in Stage 1.
